# contract プロファイル — 契約書・NDA・発注書

電子署名法準拠の観点で監査する。契約書は「署名者が誰か」が本質なので、
暗号学的完全性だけでなく身元評価（trust チェーン）の比重が最も高い。

## 必須チェック

1. **署名必須** — 未署名は human_review_required（「電子サイン系サービスの画像貼付のみ」の
   可能性を注記。それは電子署名ではない）
2. `verify_signatures` — trust_anchors を強く推奨。相手方の CA / 電子契約サービスの CA
   証明書の入手をユーザーに促す。`check_revocation: "embedded"` で始め、失効情報が
   unknown なら `online` の実行可否をユーザーに確認
3. `verify_integrity` — 署名後の増分更新を確認。連署（複数署名）は正常。
   DocMDP 違反は human_review_required。**verify v0.10.0+ なら `revisions[]` の
   `role` で連署と本文追記を読み分けられる**（署名辞書 + widget + AcroForm が増えていれば連署、
   注釈やページのコンテンツストリームが書き換わっていれば追記）。
   契約書では**どちらであるかが争点そのもの**なので、推測でなくこの内訳を根拠にする
   （手順は SKILL.md「Phase 2.5」）
4. 署名時刻 — /M・signed attribute・タイムスタンプ genTime を突き合わせ、
   大きな食い違いがあれば注記（契約成立時点の争いに直結するため）

## 推奨チェック

- `detect_pades_level` — B-T 以上（タイムスタンプ付き）を推奨。B-B のみなら
  「証明書失効後に検証不能になる」旨を推奨アクションに書く
- 複数署名の場合、各署名の ByteRange が段階的に全体を覆っているか（後の署名が
  前の署名を含む増分更新になっているのが正常形）

## 判定の上書き

> **注**: この上書き条件は pdf-verify-mcp v0.7.0 の `evaluate_policy` ルールエンジンにコード化済み。通常は engine の verdict に反映されて返るため、ここを LLM が適用するのは evaluate_policy が使えないフォールバック時のみ。

- trust: not_evaluated のままの trust_and_use は出さない（契約書で身元未評価は
  「注意して使う」が上限）

## 法令根拠（houki-egov）

- 電子署名法 第三条（真正な成立の推定）— 本人による電子署名の効力
- 電子署名法 第二条（定義）— 何が「電子署名」に当たるか
- 必要に応じ民法 第五百二十二条（契約の成立）

印紙税の質問が出たら houki-nta のタックスアンサー（電子契約は課税文書に当たらない扱い）を検索する。
